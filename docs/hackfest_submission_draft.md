## SECTION 2 — UNDERSTANDING OF THE PROBLEM

### Problem Statement

Citizens are often eligible for multiple government welfare schemes at the same time, but
schemes frequently overlap, conflict, or are mutually exclusive with each other. There is no
practical way for an ordinary citizen to determine the full set of schemes they qualify for,
which of those schemes conflict with one another, or which combination of schemes would
maximize the benefit they actually receive.

### Problem Analysis / Background

Scheme information today is scattered across dozens of department websites, PDFs, and
circulars, written in legal/administrative language. Eligibility criteria vary independently
across income, social category, location, land holding, occupation, age, disability status,
and more — with no single place a citizen can check all of this at once. As a result:

- Citizens frequently miss schemes they actually qualify for, simply because they never found
  out the scheme existed or that they were eligible.
- Citizens apply for schemes that turn out to be mutually exclusive, wasting effort and time on
  an application that was never going to be approved alongside another they already hold.
- Document requirements differ per scheme and are never reconciled against what the citizen
  already has on hand, so citizens discover missing paperwork late, after starting an
  application.
- Assisted-service operators (Common Service Centre agents, NGO/welfare-office caseworkers)
  face the same scattered-information problem on behalf of every citizen they help, multiplying
  the burden.

This is affected by: individual citizens applying for benefits (especially those less familiar
with government processes or without formal-English literacy), and the intermediaries
(CSC operators, NGO caseworkers) who apply on their behalf.

### Proposed Solution

**ASBO (Autonomous Scheme-Bundle Optimizer for Citizens)** is an agentic system that takes a
citizen's profile — captured via a structured form or via multilingual (English/Hindi/Marathi)
conversational/voice intake — and runs it through a deterministic reasoning pipeline:

1. **Eligibility evaluation** against a structured, data-driven knowledge base of scheme rules
   (never hardcoded in application code, so new schemes/rules can be added without a code
   change).
2. **Conflict detection** among the eligible schemes, using both a declared-pairwise mechanism
   and a shared "conflict group" mechanism for schemes that are inherently mutually exclusive
   (e.g. two different housing subsidies for the same purpose).
3. **Bundle optimization** — an exact/near-exact constrained-selection algorithm chooses the
   non-conflicting subset of eligible schemes that maximizes total benefit to the citizen.
4. **Plain-language explanation** of why the recommended bundle was chosen and why any
   conflicting scheme was excluded — generated by an LLM but strictly grounded in the
   deterministic result, never allowed to alter which schemes are eligible or in the bundle.
5. **Missing-document detection**, comparing each bundled scheme's required documents against
   what the citizen has already declared.
6. **Consolidated application checklist** covering every scheme in the final bundle.

On top of this core pipeline, the system adds: a stateless one-scheme Quick Eligibility Checker
usable with zero login (e.g. to check on behalf of a friend or relative); a searchable Scheme
Catalog with English/Marathi form-filling guides; a context-aware, session-scoped browser
extension that offers form-filling help directly on a scheme's real government application
page (with strict origin-verification so it can never activate as a generic assistant
elsewhere); and a curator-reviewed Retrieval-Augmented Generation (RAG) layer that proposes
knowledge-base freshness updates from official sources — every proposed update requires
explicit human approval before it can affect any citizen-facing decision.

The core design principle, held throughout: **the AI never decides eligibility.** Every
eligibility, conflict, and bundle-optimization decision is deterministic, rule-based, and
independently traceable; the LLM is used only for explanation, translation, conversational
slot-extraction (still validated against the same rules as the structured form), and
RAG-drafted proposals that a human must approve.

## SECTION 3 — RESEARCH

### Research Conducted

- Studied real, publicly available central and state government scheme portals to ground the
  seeded knowledge base in actual eligibility rules, benefit amounts, and application
  processes — including PM-KISAN (`pmkisan.gov.in`), the National Scholarship Portal
  (`scholarships.gov.in`), the National Social Assistance Programme (`nsap.nic.in`), and
  Maharashtra's MahaDBT portal (`mahadbt.maharashtra.gov.in`) and allied state department sites
  (e.g. `sjsa.maharashtra.gov.in`, `nsmny.mahait.org`).
- For every seeded scheme's application link, the actual destination page was fetched and
  read directly (not inferred from a search snippet or assumed from an HTTP 200) before being
  marked with an honest verification status — `verified`, `unverified`, `not_available` (a
  confirmed finding that no online self-application exists, e.g. because enrollment is
  automatic), or `state_specific` (application varies by local body, so no single URL is
  presented as universal).
- Researched Retrieval-Augmented Generation architecture patterns (hybrid vector + keyword
  retrieval, chunking/embedding pipelines, curator-in-the-loop review queues) to design a
  knowledge-base freshness layer that can never silently reach a live, citizen-facing record.
- Researched Manifest V3 browser-extension architecture (host permissions, content-script
  injection gating, `webNavigation` activation triggers) to build a context-aware form
  assistant that only ever activates on a specific, session-verified application page.

### Existing Solutions / Similar Work

Existing government portals (e.g. the National Scholarship Portal, MahaDBT, UMANG) each let a
citizen browse or apply to schemes *within that one portal/department*, but none of them reason
*across* schemes from independent departments to detect conflicts or compute an optimized
combination. Third-party scheme-discovery tools that do exist are typically simple
directory/search listings; they do not perform deterministic eligibility evaluation, conflict
detection, or benefit-maximizing bundle optimization, and they do not offer form-filling
assistance grounded in the scheme's own retrieved policy text.

ASBO's differentiation is the combination of: (1) a data-driven, auditable eligibility engine
that is not an LLM, (2) genuine conflict/bundle optimization across schemes from different
issuing authorities, and (3) a strict separation between deterministic decision-making and
AI-assisted explanation/translation/drafting, with human review as a hard gate wherever AI
output could otherwise reach a live decision.

## SECTION 4 — TECHNICAL DOCUMENTATION

### Technology Stack

- **Frontend (web):** React (Vite)
- **Frontend (mobile):** React Native (Expo) — same citizen journey (onboarding, personalized
  dashboard, scheme catalog) as the web app, running in Expo Go with no native build required
- **Backend:** Python (FastAPI), fully async
- **Database:** MongoDB (local for development, MongoDB Atlas for the hosted demo) — document
  model maps naturally onto per-scheme rule sets and citizen profiles with variable/optional
  fields
- **Rule engine:** Data-driven JSON-shaped rule documents embedded per scheme — eligibility
  logic lives in data, not in application code
- **Bundle optimization:** Custom constrained-selection algorithm (exact for small N, greedy
  fallback for larger N) over the conflict graph
- **AI/LLM:** Google Gemini API — used only for explanation generation, multilingual
  translation, conversational-intake slot-extraction drafting, form-assistance explanation, and
  RAG candidate drafting; never for eligibility, conflict, or bundle decisions
- **RAG / retrieval:** Hybrid vector (Chroma) + BM25 keyword retrieval over an indexed policy
  corpus, with resumable/incremental embedding ingestion
- **Authentication:** Real accounts — `bcrypt` password hashing, `PyJWT` bearer tokens, Resend
  (HTTP API) for two-step OTP email delivery, with a graceful console/debug fallback if the
  email provider is unavailable
- **Browser extension:** Manifest V3 (Chrome), `webNavigation`-gated content-script injection,
  screenshot capture via `captureVisibleTab`
- **Testing:** Pytest (backend unit/integration — 265+ tests), Playwright (frontend/extension
  end-to-end browser testing)
- **Deployment:** Single backend container + static frontend build

### Technical Flow / System Architecture

```
Citizen (web / mobile / conversational-voice intake)
        │
        ▼
Profile Intake  ──────────────►  Citizen Profile (MongoDB)
        │
        ▼
Rule Engine  ───► Eligible Schemes (+ reasons)
        │
        ▼
Conflict Detection Engine  ───► Conflicts among eligible schemes
        │
        ▼
Bundle Optimizer  ───► Optimized, conflict-free scheme bundle
        │
        ▼
Explanation Generator (LLM, grounded) ───► Plain-language explanation
        │
        ▼
Missing-Document Detector  ───► Document gaps per bundled scheme
        │
        ▼
Checklist Generator  ───► Consolidated application checklist
        │
        ▼
Reasoning Trace (every step's input/output persisted for audit)

Supporting subsystems (independent of the above, never able to alter its output):
- Quick Scheme Eligibility Checker (stateless, no account required)
- Scheme Catalog (search + form-filling guides, English/Marathi)
- Context-Aware Form Assistance (browser extension + mobile toggle, session-scoped to one
  verified scheme's application page)
- RAG Knowledge-Base Freshness (retrieval + LLM-drafted candidate updates, held in a separate
  pending-review collection until a human curator explicitly approves)
```

### Working / Implementation Approach

A citizen enters their profile — through a structured multi-step form, or by talking/typing to
a conversational assistant in English, Hindi, or Marathi (the assistant extracts the same
profile fields turn-by-turn, validated by the identical rules the structured form uses). Once
the mandatory fields are present, the profile is evaluated against every active scheme's rules
in the knowledge base, producing the eligible set with a human-readable reason per rule. Any
schemes that conflict with each other are flagged (either via an explicitly declared conflict
pair, or a shared "conflict group" for schemes that are inherently mutually exclusive). The
Bundle Optimizer then selects the non-conflicting subset that maximizes total benefit value.
An LLM writes a plain-language explanation of the result, strictly grounded in the
already-computed bundle/conflict data (never allowed to introduce new facts). The system then
compares required documents for each scheme in the bundle against what the citizen has already
declared holding, and produces one consolidated checklist. Every step's input/output is logged
to a reasoning trace the citizen (or an operator/admin) can inspect for full transparency.

### AI/ML Details

- **Model:** Google Gemini (`gemini-flash-latest`), used purely at inference time — no
  fine-tuning or training of any model in this project.
- **Where it is used:** (1) generating the plain-language bundle explanation, grounded in
  already-computed eligibility/conflict/bundle data; (2) detecting the language of and
  translating conversational-intake messages, and translating assistant replies back, with a
  translation-guard that falls back to English if a critical value (a scheme name, amount,
  date) is not preserved in translation; (3) extracting structured profile "slots" from a
  citizen's free-form statement during conversational intake, validated afterward by the exact
  same Pydantic rules the structured form uses; (4) explaining a citizen-selected form field or
  a screenshot of a government application page, grounded only in retrieved policy text; (5)
  drafting a candidate knowledge-base update from retrieved official-source text, which is
  written only to a separate pending-review collection and can never reach the live knowledge
  base without an explicit human curator approval.
- **What it is never used for:** determining eligibility, detecting conflicts, or choosing the
  optimized bundle — all three are deterministic, rule-based, and unit-tested independent of
  any LLM call. Every LLM call has a graceful, deterministic fallback if the API is
  unreachable or rate-limited, so the core pipeline never blocks on external AI availability.
- **Retrieval/RAG:** A hybrid vector (Chroma) + BM25 keyword index over an indexed corpus of
  scheme policy text, with resumable, incremental embedding ingestion (batches upsert as they
  complete, so an interrupted ingestion run keeps real progress rather than losing it).
